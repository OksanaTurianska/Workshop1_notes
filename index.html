Специфікації — теорія та практика

⚠️ Кейс: погана специфікація

Реальна ситуація: CTO швиденько згенерував спеку через ChatGPT, передав джун-дизайнерці-кореянці.

ПроблемаНаслідок
Непов'язані між собою скріниДизайнер не розуміє, куди що ставити
Попапи "валялися out of nowhere"Питання розробників залишились без відповіді
Відсутній screen flowЗатримка передачі дизайну в розробку
Дизайнер не тестував продуктРобота «всліпу», помилкові рішення
Культурний бар'єр (кореянка + критика)Будь-який фідбек — образа, стрес

✅ Що зробила PM (виправлення)

  • Зробила sequence of screens — список екранів по порядку з назвами
  • Прописала логічний зв'язок між скрінами (screen flow)
  • Додала референси та приклади
  • Переробила спеку через Claude AI (промт → структурований документ)
  • Побудувала комунікацію за книгою The Culture Map (Ерін Мейер)
Що пропонували учасниці
  • Провести детальний Discovery з клієнтом перед написанням спеки
  • Сформувати перелік уточнюючих питань + отримати відповіді
  • Зібрати Definition of Ready (DoR) — критерії готовності до розробки
  • Попросити у клієнта definition of done для кожної фічі
  • Записувати кожен дзвінок; долучати senior-спеціалістів до перших колів
  • Обов'язковий онбординг дизайнера на продукт як користувача
  • Сесія тестування продукту + презентація свого розуміння
  • Залучити senior-дизайнера хоча б на 1 годину для менторства
  • Показати референси готових якісних робіт (UI-kit, design system)
  • Screen flow з позначками: хто → що робить → який скрін
  • Прописати всі стани кнопок, попапи, blank states
Definition of Done (DoD)

Організаційні критерії для всього проекту. Наприклад: закриті всі баги → smoke-тест → регресія → задеплоєно на prod. Однакові для різних user story в рамках проекту.

Definition of Ready (DoR)

Критерії готовності user story до взяття в розробку: проведено Discovery, додані макапи, описані всі стани кнопок, дизайн готовий.

Acceptance Criteria

Конкретні перевіряємі умови для кожної окремої user story. Відрізняються між stories. Головний фокус PM — саме вони визначають "міс" чи "хіт".

Bus-фактор = кількість людей, після раптового звільнення/відсутності яких проект впаде.

«Якщо хтось з команди, не дай Бог, з'явиться автобус — чи зможете ви працювати без цієї людини?»
  • Bus-фактор завжди має бути > 1
  • Якісна спека допомагає: документація живе не в голові однієї людини
  • Легший онбординг нових людей
  • Особливо важливо в DevOps-командах

Mermaid-діаграми — ключовий інструмент

🧜 Що таке Mermaid?

Текстовий формат для створення діаграм. Пишеш код → автоматично генерується красива схема. Назва пішла від схожості фігурних елементів на русалячий хвіст 🧜‍♀️

  • Не потрібно писати код вручну — AI генерує за промтом + специфікацією
  • FigJam автоматично конвертує Mermaid-код у редагувальну схему
  • Розробники обожнюють — допомагає зрозуміти специфікацію
  • Можна зберегти як картинку або редагувати елементи
«Розробники просто цілувати вас будуть за цю штуку.»

📝 Промт для Mermaid User Flow

PROMPTНа основі наданої специфікації згенеруй User Flow у форматі Mermaid-діаграми. Вимоги: - Покрий всі основні сценарії (happy path та edge cases) - Додай blank states там, де контент може бути відсутнім - Позначай всі стани кнопок та попапи - Назви кожен екран чітко та зрозуміло - Використовуй стандартний Mermaid синтаксис (flowchart LR або TD) [Прикріпити PDF/текст специфікації]

📝 Промт для рефакторингу специфікації

PROMPTТи — досвідчений Product Manager. Перед тобою специфікація, яку треба привести до ладу. Зроби: 1. Структурований заголовок та розділи 2. Перетвори стиль на читабельний маркдаун з таблицями 3. Визнач та чітко позначи open questions 4. Додай секцію Acceptance Criteria для кожної фічі 5. Перевір логічний зв'язок між екранами 6. Додай технічні деталі (формати файлів, ліміти, стани) Поділися асамшпнами, що ти враховував. Запропонуй питання, які можуть задати розробники. [Текст або PDF поганої специфікації]
